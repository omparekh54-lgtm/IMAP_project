01 / Experimental designControlled comparison

One dataset.
Two implementations.

Both APIs expose the same core endpoints over the same in-memory country data. That isolates framework and server behaviour instead of mixing in database or network effects.

INPUT

Shared country model

Name, cca2, cca3, region, capital, population and area. Same validation intent on both sides.

DRF

Serializer-driven

Django REST Framework uses serializers, Gunicorn and Django's larger application ecosystem.

FASTAPI

Type-hint driven

FastAPI uses Pydantic, Uvicorn, automatic OpenAPI and native async request handling.

04 / Recorded benchmarkCommitted experimental evidence

CRUD was close.
Concurrency was not.

Run-to-run noise was large enough that normal CRUD throughput should be treated as roughly comparable. The slow-I/O configuration test is where the architecture difference becomes visually obvious.

MOST IMPORTANT FINDING

WAIT PER REQUEST0.2s20 concurrent requests

Once DRF receives 20 threads, it lands within noise of FastAPI for this 20-request wait test. So the first 19× gap is a concurrency-configuration effect, not proof that FastAPI is universally 19× faster.

06 / Framework decisionRequirement-driven

Which one
should you choose?

Select what your product needs. The recommendation is intentionally based on ecosystem and architecture fit, not just benchmark speed.

RECOMMENDATION
Select requirements

Choose one or more product needs above and the reasoning will update here.

There is no universal winner.
There is a better fit.

Our experiment found ordinary CRUD throughput to be broadly comparable. FastAPI offered a smaller implementation, built-in OpenAPI docs and straightforward async I/O. DRF remained compelling when the surrounding Django ecosystem — ORM, migrations, admin, auth and permissions — is the real requirement.
